# 第一周「幽冥勾名」与「第三回总试炼」设计规格

## 完成边界

- 目标证据级别：`w1-m4` 和 `w1-m5` 各达到 **One-level playable**。
- 只有当两关的真实 Blockly 输入、状态转换、失败、持久化、刷新、恢复和五浏览器项目证据都齐全时，才可称为该级别。
- 只有五关逐关自动路径、所有独立交互模式和边界证据齐全时，才声明“第一周内容已全量验证”。
- 其余25关、完整成长/奖励/装备/神兽/伙伴、全站发布仍为 `not complete`。

## 已批准的产品规则

1. 孩子在屏幕上真实连接的 Blockly 图是唯一指令源。运行时只使用从连接图编译的、带 `instructionId/sourceBlockId` 的确定性 trace。
2. 帮助只解释观察、思路和半成品方向；不连接、排序、删除、运行或完成积木。
3. 错误逻辑会让场景停在对应中间状态，并把焦点返还问题积木。不扣生命、资源或星级，不使用恐惧或责罚文案。
4. `w1-m4` 完成后解锁 `w1-m5`；`w1-m5` 完成后第一周为 5/5，但不自动把后续内容认定为已实现。

## 方案比较与选择

### 方案 A：复制 w1-m3 两次

每关各自复制 Blockly、编译、场景、会话与反馈组件。优点是文件边界直观；缺点是两套存储与恢复逻辑容易分叉，且显著放大维护面和 bundle。

### 方案 B：通用的第一周高阶关卡内核（选用）

建立一个零 UI 依赖的中性合约，定义两关各自的 block/opcode/state/scope；共用草稿序列化、图结构编译、Progress V3 会话和可访问性外壳，但两关使用不同状态机、积木词汇和场景。优点是唯一真源、更小的重复面和一致的恢复语义；风险是通用化必须严格限于这两关，不提前抽象未实现的25关。

### 方案 C：保留兼容工具并包装场景

改造成本最低，但仍以平铺 `expectedSequence` 为第二真源，无法证明真实 Blockly、图结构、独立 Boss 交互和 Progress V3 会话，不采用。

## w1-m4 玩家闭环

### 可见积木程序

顶层链为：

1. `打开名册`
2. `查找猴属记录`（容器）
3. `处理已找到的名号`
4. `核对名册结果`

查找容器的子链为：`读取索引 → 匹配猴属 → 收集有名记录`。子链不完整、容器外放置、顶层顺序错误、重复指令和提前处理都是独立可理解的失败。

### 状态与可见结果

`closed → opened → index-read → monkey-kind-matched → named-records-collected → names-handled → verified`。场景使用“整理名册”和“已处理”的儿童友好表达，不显示伤害、恐惧或惩罚。每个 accepted/rejected 事件都带原积木 ID，场景转换只读 trace。

## w1-m5 Boss 玩家闭环

Boss 是“第三回行程调度台”，不是五个旧答案的平铺拼接。孩子建立一条顶层计划，并在三个任务容器内完成不同类型的算法检查：

- 顶层：`制定第三回计划 → 龙宫检查点 → 披挂检查点 → 名册检查点 → 验证因果链`。
- 龙宫子链：`进入龙宫 → 比较兵器重量 → 选定可变化的金箍棒`。
- 披挂子链：`拆分三件礼物 → 验证披挂齐全`。
- 名册子链：`打开名册 → 查找猴属记录 → 处理匹配名号`。

状态机以检查点为单位验证“顺序、比较、任务分解、查找处理”，必须先完成当前容器才能进入下一检查点。因此成功来自一个新的分层程序，而不是路由、配置、隐藏状态或旧关答案。

## Progress V3 与跨系统

- `ExecutableMissionId` 扩展为 `w1-m1` 至 `w1-m5`；两关各自保存 workspace、lastTrace、lastRun、运行/编译失败、提示层级、时间和概念失败。
- 导入时严格验证字段、边界、图连接、编译结果和状态机重放结果；伪造 trace/run、跨容器连接、重复 ID、循环或超限数据均 fail closed。
- 现有 CAS/Web Lock、多标签冲突、未发布交易、损坏原文保留、家长导入导出和清空回滚语义不另起炉灶。
- 周报会累计五关会话的 runs/adjustments/support；`w1-m4` 对应“查找与处理”，`w1-m5` 对应“综合算法规划”。

## 视觉资产

- 继承现有宣纸、朱砂、青玉、金色体系和儿童绘本低细节风格，不重设导航、字体或卡片密度。
- 新资产仅为：幽冥文书房背景、名册状态精灵表、Boss 行程图背景、Boss 检查点精灵表。现有已批准悟空素材可复用，不复制生成。
- 所有新图像使用内置 image generation，转换为 WebP 后记录完整 prompt、尺寸、SHA-256、slot、provenance 和原分辨率视觉 QA。场景不使用 CSS/div/SVG/emoji 伪造插画或特效。

## 实施前支持矩阵与固定预算

| 项目 | 本轮固定目标 |
| --- | --- |
| 浏览器/视口 | Chromium 1440×1024；WebKit 768×1024；Chromium 390×844 touch；Firefox 1440×1024；Chromium 320×844 touch |
| 输入 | 鼠标、触摸、纯键盘；所有可见启用控件有 44×44 CSS px 目标 |
| 响应式 | 320px 不出现整页水平溢出；积木图、场景、主操作和反馈不裁切 |
| 减弱动画/静音 | 系统设置与手动覆盖均保持功能等价；静音不触发音频播放 |
| 生产 entry | 保持 180 KiB gzip，禁止 Blockly/Phaser 进入静态入口闭包 |
| 首页 | 保持 650 KiB 保守响应体预算 |
| 旧关冷加载 | w1-m1/w1-m2 保持 2.5 MiB；w1-m3 保持 2.75 MiB |
| 新关冷加载 | w1-m4 与 w1-m5 各固定为 3.0 MiB；不在实现后上调 |
| 媒体 | 保持单图 512 KiB；正式任务图像总量 1.25 MiB |

## 可执行验收

1. 课程与源码合同防止 w1-m4/w1-m5 携带 `expectedSequence`、进入 legacy tools、隐藏写完成或绕过可见 Blockly。
2. 编译器从实际连接图生成稳定 trace，严格拒绝多链头、断链、循环、非法 scope 和超限图。
3. 两个状态机覆盖正确、顺序错误、内容不完整、重复和同指令在不同状态下的结果，且 penalty 始终为 0/0/0。
4. Progress V3 覆盖草稿、trace、run、提示、尝试、完成、刷新、导入导出、损坏恢复、存储失败和多标签 CAS。
5. 五项目真实浏览器使用孩子可见操作完成“错误 → 修改 → 成功 → 刷新恢复 → 重放”，并覆盖键盘、静音/减弱动画、加载失败、404、冷加载和控制台健康。
6. 最终重跑前三关、全量 Playwright、unit、typecheck、asset、bundle/source-contract、production build 和 official npm audit；E2E 后重建 `dist`、删除 `dist-e2e`并确认无 fault sentinel。
