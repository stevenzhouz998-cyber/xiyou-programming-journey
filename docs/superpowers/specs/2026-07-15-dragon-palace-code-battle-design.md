# 龙宫试兵：真实代码战斗纵切设计

## 目标与完成边界

本子项目把第一关“龙宫求兵”改造成《西游编程记》的首个真实代码战斗纵切。孩子实际连接的 Blockly 积木必须成为唯一可执行输入；代码轨迹逐条驱动场景，错误逻辑产生可理解的错误结果，但不扣生命、不损失资源，也不替孩子完成任务。

本子项目预选完成等级为 **One-level playable（一关可玩）**。只有第一关在真实浏览器中完成输入、执行、失败、修改、成功、持久化、刷新和恢复闭环后，才能使用该等级。其余 29 关、Python、AI、成长、奖励、装备、神兽、整站发布和商业生产完成均明确排除，继续判定为 `not complete`。

## 现状与必须消除的空壳行为

- 当前通关依据是 React 内部的 `sequence` 数组，不是可见 Blockly 工作区。拖动、删除、改字或断开积木不会真实改变执行结果。
- Blockly 外观与执行数组分开保存；刷新只能恢复外观，不能恢复相同的可执行轨迹。
- 场景目前只按提交步骤数量移动同一角色图片；相同长度的正确与错误代码会得到相同动画。
- 关卡校验只是把字符串数组和预设答案做完全匹配，尚不存在逐指令执行、战斗状态、失败位置或回放证据。
- 失败尝试、提示使用、积木草稿和运行输出尚未形成同一份可靠存档。

这些行为必须被真实执行链替换，不能以新增动画、提示文字或更多配置掩盖。

## 方案选择

采用以下执行路径：

`真实 Blockly 工作区 → 类型化指令轨迹 → 确定性战斗执行器 → 场景事件流 → Phaser 演出 → 进度与家长报告`

未采用的方案：

- 不直接执行 Blockly 生成的任意 JavaScript。该方案扩展性高，但儿童输入的安全隔离、错误定位和中文反馈成本更高，不适合作为首个纵切。
- 不为每关写死独立动画状态机。该方案开发快，但无法证明代码驱动场景，也不能为后续 30 关提供可复用协议。

## 玩家循环

1. 孩子从指令匣选择并连接“进入龙宫”“请求兵器”“试用兵器”等真实 Blockly 积木。
2. 点击“执行战斗指令”后，系统只读取 Blockly 工作区。按钮点击记录、隐藏数组和预设答案均不得作为执行输入。
3. 编译器从唯一连接的顶层积木链生成类型化指令轨迹。
4. 战斗执行器逐条执行轨迹并产生场景事件，悟空、龙王和兵器严格按事件变化。
5. 空工作区、多个顶层积木链、非法连接或损坏积木会阻止运行；语义上缺少指令或顺序错误时，执行在对应步骤暂停，场景展示真实后果，反馈说明发生了什么以及应观察哪里。
6. 孩子修改积木后从头重跑。失败不扣生命、不消耗资源、不降低已有成绩。
7. 成功后才记录完成、解锁下一关，并把掌握情况和困难步骤写入家长报告。
8. 积木草稿、最近轨迹、运行结果、失败步骤、尝试次数和提示次数全部持久化，刷新后恢复到同一可执行状态。

## 核心模块与职责

### BlocklyWorkspace

- 提供积木选择、连接、重排、删除和键盘操作。
- 键盘路径操作的仍是同一个 Blockly 工作区：选择指令后必须创建真实积木并建立真实连接，不能维护一份替代数组。
- 只维护 Blockly 工作区和其序列化数据，不维护独立指令数组。
- 显示当前可执行链，但展示内容也必须来自编译结果。
- 工作区变化后通过统一会话接口保存草稿；不得自行直接写入另一个旁路存储。

### BlocklyCompiler

- 从实际连接的顶层积木链读取指令。
- 产出版本化、可序列化的类型化指令轨迹。
- 检测多个顶层链（含孤立或断开的链）、未知积木、空工作区和不允许的连接形状。
- 返回结构化诊断信息，包括问题类型、积木 ID、轨迹位置和儿童可理解的反馈代码。
- 不判断关卡是否成功，只负责把孩子真实搭建的程序翻译为可执行输入。

每个轨迹项必须包含稳定的 `instructionId`、Blockly 的 `sourceBlockId` 和类型化 `opcode`。`instructionId` 由保存后仍稳定的 Blockly block ID 派生；编译、执行、事件、反馈和运行摘要全程保留这两个 ID，确保运行时失败和刷新后的回放都能定位回同一块真实积木。

### BattleEngine

- 以关卡战斗定义、初始状态和类型化指令轨迹为输入。
- 按顺序执行每条指令，产出确定性的场景事件和最终结果。
- 第一关至少包含进入龙宫、提出请求、试用兵器三个可观察状态变化。
- 错误逻辑产生对应的错误动作并暂停，不允许自动纠正、跳过或补全指令。
- 结果包含成功或失败、停止步骤、事件流和可持久化的运行摘要。
- 不操作 DOM、Blockly、Phaser 或本地存储，以便独立测试和复用。

第一关的确定性状态依次为 `outside-palace → entered-palace → weapon-requested → weapon-tested`。三条指令各自只接受前一状态；在其他状态执行时产生 `instruction-rejected` 事件并停止。轨迹结束且最终状态为 `weapon-tested` 时，纯结果判定返回 `completed: true`，不再执行隐藏指令或额外状态转移。每次运行从 `outside-palace` 开始，事件流至少包含运行开始、指令接受或拒绝、状态变化和运行结束。这样测试可以逐项证明错误顺序确实改变了场景结果，而不是只比较最终答案。

BattleEngine 不接收也不得读取 `expectedSequence`。它只根据当前状态和当前 `opcode` 的前置条件做一次状态转移。每个指令事件必须回传原轨迹的 `instructionId/sourceBlockId`。合法前缀可独立推进到对应中间状态；相同长度但不同错误轨迹、重复指令以及同一指令在不同状态下必须产生各自对应的中间状态和拒绝事件，不能落入同一份罐头失败动画。

### GameScene

- 只消费 BattleEngine 事件流并播放正式资产。
- 不根据积木数量、预设答案或完成状态自行判断剧情。
- 支持标准动画和减少动态效果两种表现；两种模式的状态结果必须一致。
- 支持从已保存的运行摘要恢复最终画面，并可从头回放最近一次执行。

### MissionSession

每关会话至少保存：

- 版本化 Blockly 草稿；
- 编译后的最近指令轨迹；
- 最近运行事件摘要和结果；
- 失败步骤与诊断代码；
- 总运行次数、运行失败次数、编译失败次数、已使用提示层级和困难概念计数；
- 最近运行时间和保存时间。

会话必须进入现有事务式存档体系，随导出、导入、快照和损坏恢复一起工作。实现时新增严格的 `ProgressV3`：在 V2 字段基础上增加按关卡 ID 索引的 `sessions`，并提供 V1、V2 到 V3 的无损迁移。V3 仍须拒绝未知字段、无效关卡 ID、非法数字、损坏 Blockly 数据和不规范时间。不得继续使用 `xiyou-workspace-*` 独立旁路作为正式存档真源；迁移可读取旧键一次，验证成功并写入 V3 后才允许移除旧键。

### ProgressContext 与家长报告

- 通过现有事务式存储保存 ProgressV3 中的 MissionSession 和关卡完成结果。
- 存储失败时保留内存中的本次编辑，固定显示“尚未保存”，并允许重试。
- 只有真实执行成功才能解锁下一关。
- 家长报告展示尝试次数、困难概念和是否需要支持，不展示代码全文或额外儿童个人信息。

计数口径固定如下：只有编译成功并启动 BattleEngine 才增加一次“总运行次数”；`instruction-rejected` 或 `program-ended-incomplete` 增加一次“运行失败次数”；被编译器阻止的每次明确运行操作增加一次“编译失败次数”。同一提示层级在该关首次展开时记录一次，重复收起和展开不重复计数。诊断映射为三类稳定概念：空工作区、多个顶层链、非法连接和未知积木映射为“程序结构”；状态前置条件不满足映射为“顺序与前置条件”；缺少完成步骤映射为“完整性检查”。同一概念累计两次失败或使用两个以上提示层级时，家长报告标记“建议关注”；以上规则必须由测试锁定。

## 状态与数据流

唯一数据链如下：

1. 孩子编辑 Blockly 工作区。
2. 工作区序列化后进入 MissionSession 草稿。
3. 运行时，BlocklyCompiler 从该工作区生成指令轨迹。
4. BattleEngine 消费轨迹并产生事件流与结果。
5. GameScene 播放同一事件流。
6. MissionSession 保存轨迹、事件摘要、失败位置和尝试数据。
7. 成功结果更新关卡进度、下一关解锁和家长报告。

任何下游模块都不得重新推断另一份“正确答案执行轨迹”。刷新、导出、导入和损坏恢复后，草稿必须重新编译出与保存前相同的 `instructionId/sourceBlockId/opcode` 轨迹。

## 失败体验与辅助边界

### 编译前失败

- 空工作区：提示先放入第一条指令。
- 存在多个顶层链（包括孤立或断开的另一段积木）：说明程序有多个开头，并高亮除主链外的第一块积木，要求孩子连接成一条主链。
- 存在不允许的输入、输出或连接形状：指出连接位置无效并高亮对应积木。
- 未知或损坏积木：保留原始草稿，禁止静默删除；提供备份下载和恢复入口。

编译诊断使用固定优先级，保证同一工作区每次得到相同首要反馈：未知或损坏积木 → 不允许的连接形状 → 多个顶层链 → 空工作区。一次可以保存全部诊断，但界面先呈现优先级最高的一项。

### 运行时失败

- 顺序错误时，执行到相关步骤暂停；轨迹合法但结束在 `weapon-tested` 之前时，产生 `program-ended-incomplete` 运行级诊断。
- 场景必须展示逻辑造成的真实结果，例如尚未提出请求就试图取兵器时，龙王不会交出兵器。
- 由实际错误指令触发的 `instruction-rejected` 必须携带 `instructionId/sourceBlockId`；反馈中的“回到问题积木”聚焦并高亮对应 Blockly 积木，刷新后该映射仍然有效。
- `program-ended-incomplete` 没有不存在的来源积木 ID。它聚焦工作区；若存在最后一块有效积木，则高亮该积木并提示“在这里之后还缺一步”，否则提示从第一条指令开始。
- 反馈只解释已发生的结果和需要观察的位置，不提供完整正确顺序。
- 重试从确定的初始状态开始，避免上次失败残留改变下一次结果。

### 无惩罚与提示

- 失败不扣生命、不扣资源、不回退关卡、不降低已获得星级。
- 失败尝试只用于提供支持建议和家长报告。
- 提示分为观察场景、思考因果、局部提示三级。
- 提示不得自动连接、排序、删除、重写、攻击、执行或完成任务。

### 存储与恢复失败

- 写入失败时明确显示未保存状态，不得声称刷新安全。
- 重试保存成功前，孩子可以继续编辑和运行。
- 导入、损坏恢复和清除继续遵守现有备份优先、原始损坏源保留和回滚规则。

## 界面与无障碍

- 手机端采用“场景 → 积木 → 运行反馈”的纵向结构。
- 桌面端采用场景与工作台并列结构，但两端使用同一执行规则。
- 支持 320、390、768 和 1440 像素目标宽度，不出现关键控件横向溢出。
- 键盘用户能完成选块、连接、重排、删除、运行、修改和重试。
- 编译或运行失败后，焦点移动到可理解的反馈区域，并提供返回问题积木的操作。
- 开启减少动态效果后，逐条动画改为即时状态切换，事件顺序和最终结果不变。
- 静音设置覆盖本关全部声音反馈。

## 正式美术资产

第一关至少需要以下正式资产类别：

- 龙宫战斗/试兵背景；
- 少年悟空角色状态；
- 龙王角色状态；
- 三种试用兵器；
- 成功、受阻和指令命中反馈特效。

这些资产必须由环境内置图像生成或编辑工具制作，或来自已批准且可验证的现有来源。每项发布资产必须在项目级 `docs/assets/asset-manifest.md` 清单中恰好有一条完整记录，包含稳定 ID、内容哈希、用途、工具或来源、提示词或来源引用、尺寸、许可/来源状态、使用位置和 QA 状态。

Phaser 只能摆放、裁切、着色、过渡和动画正式资产，不得用 emoji、CSS art、div art、手写 SVG、代码画布、ASCII 或占位框冒充成品美术。资产先完成来源核验，再由实际文件检查以及 320、390、768、1440 像素目标视口截图审查确认裁切、清晰度、角色一致性和界面可读性，才可标记 `visual-qa-passed` 并进入发布目录；本子项目不得把未完成美术包装成商业级完成。

## 测试策略与可执行验收

实现必须遵循测试先行。每项行为先出现能失败的测试或可执行验收，再实现通过。

### 单元与集成测试

- 实际连接的 Blockly 主链能编译成唯一指令轨迹。
- 重排、删除、断开、多个顶层链、未知积木和空工作区得到确定结果。
- BattleEngine 不读取预设答案；每条指令只按当前状态和自身前置条件产生确定事件。
- 合法前缀、同长度不同错误轨迹、重复指令和同一指令在不同状态下产生不同且可追溯的中间状态或拒绝事件。
- 对实际指令，编译轨迹、场景事件、失败反馈和刷新恢复全程保留稳定 `instructionId/sourceBlockId` 并能定位真实积木；缺少指令使用无伪造 ID 的 `program-ended-incomplete` 诊断。
- 失败不会扣生命、资源、星级或已有完成记录。
- MissionSession 覆盖草稿、轨迹、事件摘要、失败位置、尝试次数和提示次数。
- 编译失败、运行失败、提示层级和困难概念严格按已定义口径计数，重复打开提示不重复计数。
- 刷新、导出、导入、V1/V2 到 V3 迁移、旧 Blockly 键迁移、损坏恢复、写入失败和重试保存均保留同一可执行状态。
- 减少动态效果与标准动画得到相同最终状态。

### 真实浏览器路径

浏览器测试必须使用孩子式操作真实积木，不得调用隐藏函数、直接写成功状态或预填正确答案。

完整路径至少覆盖：

1. 搭建错误程序并运行；
2. 场景在对应错误步骤暂停；
3. 反馈定位问题但不提供完整答案；
4. 孩子重排或补充真实积木；
5. 第二次执行成功；
6. 刷新后恢复积木、最近轨迹和完成状态；
7. 下一关解锁；
8. 家长报告显示真实尝试与困难数据；
9. 导出再导入后再次恢复同一状态；
10. 存储失败时显示未保存，重试后恢复已保存状态。
11. 注入包含 Blockly 草稿的损坏 V3 存档，原始字节被保留并可下载；从快照或导入恢复后，真实工作区重新编译出恢复前相同的 ID 和执行轨迹。

浏览器矩阵固定如下：

- 完整“错误运行 → 修改 → 成功 → 刷新 → 解锁 → 家长报告”路径运行于 Chromium 1440、Chromium 390、Firefox 1440 和 WebKit 768。
- 320 像素 Chromium 额外覆盖从打开关卡到成功的完整路径及无横向溢出。
- 键盘完整路径运行于 Chromium 1440 和 Firefox 1440，所有操作必须改变同一 Blockly 工作区。
- 减少动态效果与静音路径运行于 Chromium 390 和 WebKit 768，并断言最终状态及事件顺序与标准模式一致。
- 损坏 V3 会话、原始字节下载、快照恢复和重新编译轨迹在 Chromium 1440 完整运行；Firefox 1440 与 WebKit 768 至少验证恢复后草稿可见、ID 稳定并能再次成功执行。

### 回归与性能门禁

- 现有 159 条单元测试、14 条构建门禁和 40 条商业基础浏览器测试不得回退。
- 入口静态 JavaScript 不超过 180 KiB gzip。
- 保守首屏资源不超过 650 KiB。
- Phaser 动态包不超过 1600 KiB raw，并继续保持按需加载。
- 第一关冷加载全部响应体不超过 2.5 MiB；其中第一关新增图片与音频合计不超过 1.25 MiB，任何单张发布位图不超过 512 KiB。浏览器测试以禁用缓存后的实际响应体计量。
- 正式资产清单必须与构建输出逐项匹配；缺失、额外、来源不明或哈希不匹配均失败。
- 每个发布资产必须在清单中恰好出现一次，且只有具备实际文件检查与 320、390、768、1440 截图证据的资产才能标记 `visual-qa-passed`。
- `git diff --check`、类型检查、生产构建和占位符/禁用资产扫描必须通过。
