# w1-m3 四海披挂代码战斗设计规格

## 目标与完成边界

本子项目把 `w1-m3 四海披挂` 从明确标记的 Legacy 兼容路径升级为第三个真实 Blockly、代码驱动场景、Progress V3 持久化的完整可玩关卡。

预选完成等级只有：

- `w1-m3 四海披挂：One-level playable`，前提是本规格的自动化、正式资产和五项目真实浏览器证据全部通过。
- `w1-m1 龙宫求兵` 与 `w1-m2 定海神针`：继续保持各自已验证的 `One-level playable`。
- 本地 Parent / saves 基础：继续保持已验证的 `System loop complete for the implemented local foundation only`。
- `w1-m4` 至 `w6-m5`、完整成长/奖励/装备/神兽/伙伴/战斗体系、公开部署与整站：`not complete`。

本关出现的金冠、金甲和云履是第三回故事内的关卡状态，不是全站可获取、可穿脱或改变后续选择的装备系统。在这些跨关效果实现前，不得宣称装备系统完成。

## 现状差距审计

已验证起点 `f19ff2968888c82f88a451db844e5552f7bc3798` 的非浏览器基线为 575 个 Vitest 单元测试、24 个体积规则测试、27 个资产测试、TypeScript `--noEmit`、生产 build、bundle gate 和正式资产 gate 全绿。

当前 `w1-m3` 仍有以下缺口：

- 路由使用 `MissionTools -> LegacyMissionBuilder + LegacyGameScene`，不是真实 Blockly 可执行会话。
- 可见 React 数组只校验平铺顺序，没有嵌套任务分解语义、稳定 block ID 或编译来源。
- `Progress V3` 的 `MissionSessionById`、严格 schema、`ProgressContext.updateMissionSession`、会话支持推导和家长周报只识别 `w1-m1/w1-m2`。
- 没有 w1-m3 任务专属积木白名单、草稿恢复、编译器、确定性状态机、诊断、播放和完成门禁。
- Legacy 场景依赖来源不完整的 `world-map.jpg` 与 `young-hero.jpg`，不能用作本关正式资产证据。
- 没有 w1-m3 专属 lazy 边界、冷加载预算、五项目真实孩子路径、损坏恢复、父母导出导入或原尺寸截图 QA。

因此，只替换页面文案、增加配置或给 Legacy 工具换名，不能达到本关的完成等级。

## 原著与学习目标

第三回原著中，悟空得到定海神针后再求披挂。三海龙王报出宝物的顺序是：

1. 北海龙王敖顺：藕丝步云履；
2. 西海龙王敖闰：锁子黄金甲；
3. 南海龙王敖钦：凤翅紫金冠。

随后悟空按“金冠、金甲、云履”穿戴停当。这为“分解任务”提供两个语义不同的子任务组：先收齐宝物，再按穿戴顺序完成披挂。

孩子要学会：

- 把“完成一副披挂”拆成“请求→收集→穿戴→检查”主任务；
- 把收集与穿戴各自拆成三个有顺序的子任务；
- 理解子任务必须放在正确任务组中，不能只靠名字相似或系统暗中排序；
- 通过错误播放和诊断修正自己的可见代码。

## 方案比较与已确认选择

### 方案 A：两个真实嵌套子任务组（已采用）

主链包含请求、收集组、穿戴组与最终检查。两个容器块各自通过 Blockly statement input 包含孩子真实连接的子任务。编译轨迹保留容器 block ID、子任务 block ID 与所属容器。

优点是学习目标和代码结构真正一致，且形成第三种可验证交互；代价是草稿、编译器和 schema 必须安全处理嵌套连接。

### 方案 B：平铺七至八个顺序块（不采用）

实现和恢复较简单，但孩子实际只在做更长的 w1-m1 顺序题，不能证明“分解任务”。

### 方案 C：三件宝物任意顺序清单（不采用）

强调独立子目标，但会丢失原著的赠宝与穿戴次序，也减少了错误逻辑可视化的学习价值。

## 玩家输入与真实 Blockly 结构

正式工作区的积木白名单是：

### 主任务块

1. `向东海龙王请求披挂` / `request_regalia`；
2. `收齐三海宝物` / `collect_gifts`，带一个 `GIFTS` statement input；
3. `穿戴整副披挂` / `equip_regalia`，带一个 `GEAR` statement input；
4. `检查披挂是否齐全` / `verify_regalia`。

### 收集子任务块

1. `收下北海的藕丝步云履` / `receive_cloud_boots`；
2. `收下西海的锁子黄金甲` / `receive_golden_armor`；
3. `收下南海的凤翅紫金冠` / `receive_purple_crown`。

### 穿戴子任务块

1. `戴上凤翅紫金冠` / `wear_crown`；
2. `穿上锁子黄金甲` / `wear_armor`；
3. `踏上藕丝步云履` / `wear_boots`。

正确可见结构是：

```text
向东海龙王请求披挂
收齐三海宝物
  收下北海的藕丝步云履
  收下西海的锁子黄金甲
  收下南海的凤翅紫金冠
穿戴整副披挂
  戴上凤翅紫金冠
  穿上锁子黄金甲
  踏上藕丝步云履
检查披挂是否齐全
```

触屏/键盘辅助按钮只能创建、嵌套、移动或删除同一个 Blockly 工作区中的真实块。树形文本摘要从工作区现算，不是第二执行真源。

## 编译轨迹与结构证明

编译器只接受一条主链，并验证两个容器的 statement connection 与子链连接都是 Blockly 的真实双向连接。它拒绝：

- 空工作区、多个顶层主链、断裂/伪造连接、循环、未知积木；
- w1-m1 或 w1-m2 积木混入；
- 容器没有子任务连接，或子任务不能无损表示；
- 超过 schema 限额的块数、ID 或坐标。

编译结果是平坦的确定性指令列表，但每条指令保留：

```ts
interface FourSeasInstruction {
  instructionId: string
  sourceBlockId: string
  opcode: FourSeasOpcode
  parentBlockId: string | null
}
```

顶层块的 `parentBlockId` 为 `null`；子任务的 `parentBlockId` 是所属容器的真实 block ID。编译器按可见主链与容器内子链的前序生成轨迹。重排、删除、换容器或断开任何一块后，轨迹必须跟随变化。

## 代码驱动状态机

可见场景状态：

- `awaiting-request`：尚未请求披挂；
- `regalia-requested`：东海龙王已召来三海龙王；
- `collecting-gifts`：已进入收集子任务；
- `cloud-boots-received`：云履已收下；
- `golden-armor-received`：金甲已收下；
- `all-gifts-received`：金冠收下，三件宝物齐备；
- `equipping-regalia`：已进入穿戴子任务；
- `crown-equipped`：金冠已戴；
- `armor-equipped`：金甲已穿；
- `regalia-equipped`：云履已踏，整副披挂穿戴完毕；
- `regalia-verified`：检查通过，关卡完成。

状态机严格要求上述可见结构和原著顺序。`collect_gifts` 和 `equip_regalia` 指令必须位于顶层；子任务必须引用正确容器的 block ID。

以下都是可见失败：

- 未请求就收宝、未收齐就穿戴、未穿齐就检查；
- 收宝顺序错误、穿戴顺序错误、重复子任务；
- 子任务放在错误容器中；
- 主链或子链提前结束。

运行错误携带实际问题积木的 `instructionId/sourceBlockId/parentBlockId`，场景播放错误送宝、提前穿戴或检查被拦下的结果，反馈按钮把焦点送回同一块真实积木。所有运行固定记录零惩罚：`livesLost = resourcesLost = starsLost = 0`。

只有最终 `verify_regalia` 到达 `regalia-verified`、运行会话已经安全写入且完成播放后，才能进入关卡完成写入。编译成功、点击运行、场景加载或重播都不得通关。

## 正式场景与资产

w1-m3 继续处于龙宫，可复用已通过来源和视觉 QA 的龙宫背景、悟空、龙王与效果图。本关新增的披挂语义无法由既有兵器图表达，因此必须使用环境内置 image generation/editing 工具生成：

1. `regalia.webp`：透明背景的凤翅紫金冠、锁子黄金甲、藕丝步云履三物正式图；
2. `wukong-regalia.webp`：与已批准悟空角色风格一致、完整穿戴三件披挂的悟空正式图。

内置工具输出先经原尺寸查看，必要时只做透明度处理与 WebP 技术编码。资产清单必须记录目的、内置工具、完整提示词、尺寸、SHA-256、来源状态、实际屏位和 `visual-qa-passed`。

Phaser 只能定位、裁切、缩放、着色或过渡已批准图像。不得用 emoji、CSS/div art、手写 SVG、代码 Canvas 绘图、占位框或文字冒充披挂插画。

## Progress V3、刷新与损坏恢复

`progress.sessions['w1-m3']` 沿用已验证会话合同：

- 版本化、可无损恢复嵌套连接的 Blockly workspace draft；
- 最后一次真实编译轨迹，包含稳定块 ID 和容器来源；
- 最后一次确定性运行结果与事件；
- 总运行次数、运行失败、编译失败、使用过的提示层级和概念失败；
- 最后运行时间和保存时间。

Progress V3 严格解析器按 session key 分派 w1-m1、w1-m2 和 w1-m3 的草稿、指令、状态、事件、诊断与 canonical run。任意篡改、跨关积木、伪造父容器、不一致运行结果或未升级关卡的 session 都必须被拒绝。

草稿、运行、提示与完成写入继续通过 `ProgressContext` 和 storage coordinator；禁止组件直接写 `localStorage`。保留 Web Locks + revision CAS、多标签冲突、真实清空、损坏原始字节保留和无锁 fail-closed。

刷新后必须恢复同一嵌套结构、block ID、编译轨迹、最后事件、场景状态和计数，但不自动再次完成。当前 V3 损坏时，家长下载保留原始损坏字节，合法 snapshot 恢复的稳定 block ID 仍能通过可见操作继续执行。

## 跨关与家长影响

- w1-m3 完成且安全持久化后解锁 `w1-m4 幽冥勾名`，刷新后仍解锁。
- 不同提示层级的使用数继续决定 3/2/1 星。
- w1-m3 的 attempts、hints、运行次数和调整次数进入第一周家长周报。
- 重复失败必须把“任务分解”或更精确的嵌套/顺序支持语句进入“需要留意”，不能只汇总前两关。
- 不新增货币、全局背包、可穿脱装备或神兽成长；因此不会伪造跨系统装备效果。

## 无障碍、安全与失败处理

- 鼠标、触屏和键盘可完成添加主任务、向指定容器添加子任务、上下移动、跨容器移动、删除、清空、运行、重播和回到问题积木。
- 树形程序摘要标出“主任务/收集子任务/穿戴子任务”，但不代替 Blockly 画布。
- 编译/运行错误使用自动聚焦的 `role=alert`；播放文本使用礼貌 live region。
- 320px 页面不发生整页水平滚动，嵌套块在 Blockly 自身可控区域内可见、可聚焦、可操作。
- reduced motion 使同一事件序列立即到达同一最终状态；执行前静音不得请求或播放成功音频。
- 嵌套 Blockly、正式场景、外层体验或存储 lazy chunk 失败时，保留故事、目标、未受影响的半区和显式重试/重载。
- Phaser 资产失败显示本地重试；所有异步播放使用 owner/generation 门禁，旧回调不得污染新场景。

## 实施前固定的性能预算

以下预算在实现前固定，不因超限而事后放宽：

- 首页入口静态 JS：不超过 180 KiB gzip；
- 首页保守总量：不超过 650 KiB；
- Phaser 动态依赖：单块不超过 1600 KiB raw；
- 每个正式 Phaser 场景运行闭包：不超过 1900 KiB raw；
- `w1-m1` 冷加载响应体：仍不超过 `2.5 * 1024 * 1024` B；
- `w1-m2` 冷加载响应体：仍不超过 `2.5 * 1024 * 1024` B；
- `w1-m3` 冷加载响应体：不超过 `2.75 * 1024 * 1024` B；
- 全部已批准龙宫任务媒体总量：仍不超过 `1.25 * 1024 * 1024` B；
- 单张 raster：不超过 512 KiB。

w1-m3 外层体验、嵌套 Blockly 工具与 Phaser 场景必须由任务路由分别动态加载，不得增大 w1-m1/w1-m2 冷路径或首页入口闭包。冷加载证据禁用缓存和 service worker，统计所有 HTTP(S) 2xx 响应体，并对请求失败、重定向、304、非 2xx 或成功响应体不可读 fail-closed。

## RED→GREEN 自动化验收

所有生产行为先写失败测试或可执行验收检查，确认失败原因是缺少目标行为，再写最小实现。

自动化必须覆盖：

- w1-m3 积木注册、主链/子链真实连接、父容器来源、重排/删除/跨容器移动和跨关块拒绝；
- 正确状态轨迹、收宝顺序错误、穿戴顺序错误、错容器、重复、不完整程序、零惩罚和确定性重放；
- 嵌套草稿保存/恢复稳定 ID，Progress V3 严格解析、canonical run、篡改拒绝、导出导入与损坏 snapshot 恢复；
- 草稿、运行与完成写入失败保留真实编辑并可重试；CAS、多标签、clear 和无锁回归不放宽；
- 完成只在会话持久化与播放结束后发生一次；刷新不重复完成；w1-m4 解锁和家长周报包含 w1-m3；
- 嵌套键盘/触屏操作、320px、reduced motion、mute、lazy 失败、资产加载失败、类型、资产清单和全部固定包体预算。

## 五项目真实浏览器证据

支持目标在实现前固定为：

1. desktop Chromium 1440×1024；
2. tablet WebKit 768×1024；
3. touch Chromium 390×844；
4. desktop Firefox 1440×1024；
5. narrow touch Chromium 320×844。

五个项目都从仅含已完成 w1-m1/w1-m2 的合法进度前置开始，不注入 w1-m3 草稿、session、轨迹、事件或完成状态。每个项目都通过可见控件：

1. 进入 w1-m3，证明不再渲染 Legacy 兼容工具或旧世界地图；
2. 创建主任务与两个真实容器；
3. 在收集容器中故意放入“南海金冠→西海金甲→北海云履”错序子任务，穿戴组按正确顺序搭建；
4. 运行并看到错误龙王/宝物提前出现、阻挡效果、精确反馈和问题积木焦点；
5. 真实移动/删除/重新添加子任务，把收集容器修正为“北海云履→西海金甲→南海金冠”；
6. 执行完整轨迹，看到三件宝物出现、悟空按金冠→金甲→云履穿戴，最终检查完成；
7. 刷新并证明嵌套连接、block ID、parentBlockId、轨迹、事件、场景状态和计数恢复；
8. 返回地图证明 w1-m4 解锁，并验证当前 viewport 无关键裁切、320px 无整页水平溢出。

附加真实浏览器路径覆盖：键盘完整嵌套编辑、写入失败与可见重试、多页冲突/外部完成、损坏 V3 snapshot 恢复、家长周报与导出导入、reduced-motion/mute 等价、三层 lazy 503、w1-m1/w1-m2 回归冷预算与 w1-m3 新冷预算。

浏览器中的 `page.evaluate` 只能用于读取证据、在首次页面加载前安装合法前置或故意存储失败/损坏装置。不得写入 w1-m3 完成、session、草稿或隐藏成功状态。
