# w1-m2 定海神针代码战斗设计规格

## 目标与完成边界

本子项目把 `w1-m2 定海神针` 从明确标注的 `LegacyMissionBuilder` 兼容交互壳，升级为第二个真实 Blockly、代码驱动战斗、Progress V3 持久化的完整可玩关卡。

预选完成等级只有：

- `w1-m2 定海神针：One-level playable`，前提是本规格的自动化与真实浏览器证据全部通过。
- `w1-m1 龙宫求兵：继续保持 One-level playable`，不得因第二关改造而回退。
- 本地 Parent / saves 基础：继续保持已验证的 `System loop complete` 边界。
- `w1-m3` 至 `w6-m5`、完整成长/奖励/装备/神兽/伙伴/战斗体系、公开部署与整站：`not complete`。

本规格不新增神兽、装备、货币或自动提示代理。神兽长期规则仍是 1 只本命 + 5 只伙伴、单只核心养成不超过七天，且辅助不得改积木、攻击或通关。

## 已确认约束

- 孩子在可见 Blockly 工作区中的真实连接关系是唯一执行输入。
- 不接受隐藏数组、预设答案、按钮点击记录、`page.evaluate` 注入通关或兼容壳冒充 Blockly。
- 错误逻辑必须播放可见的错误动作；失败不扣生命、资源或星星。
- 所有会话写入继续走 `ProgressContext`、storage coordinator、Web Locks 与 revision CAS；无锁时 fail-closed。
- 第二关必须动态加载；第一关固定 2.5 MiB 冷加载门槛不得放宽。
- 正式视觉只复用已通过来源和视觉 QA 的龙宫五张 WebP；若现有资产不能表达本规格，必须先通过内置图像工具生成并登记，不能用代码绘图或占位图替代。
- 不 push、不 deploy，不修改或丢弃主仓 `stash@{0}`。

## 学习目标与玩家输入

第二关落实课程清单中的“数值比较”，不是重复第一关的纯顺序练习。

孩子看到三件兵器的重量：

- 大捍刀：3600 斤；
- 方天画戟：7200 斤；
- 定海神针：13500 斤。

正式 Blockly 工具箱提供五种语义明确的语句积木：

1. `查看三件兵器重量`；
2. `选择大捍刀（3600斤）`；
3. `选择方天画戟（7200斤）`；
4. `选择定海神针（13500斤）`；
5. `缩小定海神针`。

正确主链是：

`查看三件兵器重量 → 选择定海神针（13500斤） → 缩小定海神针`

三块选择积木是互斥的真实程序选择。孩子必须比较可见数字并选择最大值；系统不能把任何选择积木静默改成正确答案。

键盘与触屏辅助按钮仍只创建、连接、移动和删除同一个 Blockly 工作区中的真实积木。Blockly 自身的可见画布、连接关系、序列化草稿和编译轨迹必须一致。

## 方案比较与选择

### 方案 A：在现有 w1-m1 纵切上增加任务专属领域模块，复用执行与持久化合同（采用）

- w1-m1 与 w1-m2 各自拥有积木目录、确定性状态机和场景语义。
- 两关共享稳定指令来源 ID、会话统计、Progress V3 存储协调器、Blockly 工作区外壳、反馈与恢复合同。
- App 只在进入 w1-m2 时动态加载第二关体验和 Phaser 场景。

优点是 w1-m1 的已验证行为可以保持稳定，同时第二关不是配置换皮；代价是 Progress V3 解析器必须按 mission ID 校验对应积木、操作码、状态和确定性运行结果。

### 方案 B：把两关一次性重构成完全数据驱动的通用战斗框架（不采用）

长期扩展性较强，但会同时改动第一关编译器、场景、会话、Schema 和浏览器证据，扩大回归面，也容易在尚未有第三种玩法前过度抽象。

### 方案 C：复制第一关组件并替换文案和成功条件（不采用）

短期文件改动较少，但会复制存储、播放竞态和无障碍逻辑，形成两个容易漂移的实现；若仍依赖兼容序列或隐藏状态，也违反单一真源要求。

采用方案 A。它保留任务间真实差异，只共享已经被证据证明稳定的技术合同。

## 领域模型与编译轨迹

w1-m2 的积木类型和操作码是任务专属白名单。编译器必须：

1. 拒绝空工作区、多个顶层链、断裂连接、未知积木和混入 w1-m1 的积木；
2. 从唯一顶层块沿 `next` 连接生成轨迹；
3. 为每项保留 `instructionId = instruction:<sourceBlockId>`；
4. 输出且只输出孩子可见连接链中的操作码；
5. 重排、删除或断开积木后，下一次编译结果必须随之改变。

w1-m2 操作码：

- `inspect_weights`；
- `choose_sabre`；
- `choose_halberd`；
- `choose_ruyi_staff`；
- `shrink_ruyi_staff`。

工作区草稿继续使用版本化、有限节点、稳定 ID、显式 `nextId` 和安全坐标的结构。解析和恢复必须按 session 所属 mission ID 校验白名单，不能让一关的积木在另一关执行。

## 代码战斗状态机

状态：

- `awaiting-inspection`：尚未查看重量；
- `weights-inspected`：三件兵器和重量可见；
- `wrong-weapon-selected`：选择了 3600 或 7200 斤兵器；
- `ruyi-staff-selected`：正确选择 13500 斤定海神针；
- `ruyi-staff-shrunk`：金箍棒缩小到随身大小，关卡完成。

确定性转移：

- `awaiting-inspection + inspect_weights → weights-inspected`；
- `weights-inspected + choose_sabre/choose_halberd → wrong-weapon-selected`，立即产生可见拒绝动作并结束本次运行；
- `weights-inspected + choose_ruyi_staff → ruyi-staff-selected`；
- `ruyi-staff-selected + shrink_ruyi_staff → ruyi-staff-shrunk`。

其他组合均是可见错误：例如先选择、先缩小、重复查看、正确选择后再选轻兵器、重复缩小。错误事件必须携带问题积木的 `instructionId/sourceBlockId`，反馈按钮把焦点送回同一块真实 Blockly 积木。

程序在非完成状态自然结束时给出“还缺哪一步”的不完整反馈。每次运行固定记录零惩罚：`livesLost = resourcesLost = starsLost = 0`。

只有 `ruyi-staff-shrunk` 的完成事件播放完毕后，UI 才能调用关卡完成；编译成功、点击运行或场景加载本身不能通关。重播历史事件不得重复完成或增加 attempts。

## 可见场景与正式资产

w1-m2 复用已批准的龙宫场景、悟空、龙王、三兵器图和三反馈效果图，因为故事地点、角色和兵器连续承接 w1-m1，且这些图已经有内置 image generation 来源、prompt、hash、尺寸和 QA 记录。

新增屏位必须在资产清单中精确登记为 `w1-m2`，并通过真实浏览器截图检查：

- 查看重量后同时展示三件兵器，并在邻近的真实 HTML 信息区呈现 3600、7200、13500 三个数字；数字与说明是 UI 文本，不是替代插画。
- 错选时显示对应兵器裁切、阻挡效果和明确中文说明。
- 正选时只展示定海神针。
- 缩小完成时保留定海神针并显示成功效果；Phaser 只定位、裁切、缩放和过渡正式图片，不绘制最终插画。

不得新增 emoji、CSS/div art、手写 SVG、Canvas 画出的兵器、占位框或未登记图片。

## Progress V3、刷新与损坏恢复

`progress.sessions['w1-m2']` 与 w1-m1 使用相同会话合同：

- 版本化 Blockly workspace draft；
- 最后一次真实编译轨迹；
- 最后一次确定性运行结果和事件；
- 总运行次数、运行失败次数、编译失败次数；
- 已使用提示层级；
- 概念失败计数；
- 最后运行时间和保存时间。

Progress V3 解析器按 session key 分派校验：

- `w1-m1` 只接受第一关积木、操作码、状态和 canonical run；
- `w1-m2` 只接受第二关积木、操作码、状态和 canonical run；
- 其他关卡在正式升级前不得伪造可执行 session。

编辑、运行、提示和完成仍通过 `updateMissionSession` / `complete` 进入既有事务。不得直接写 `localStorage`。

刷新必须恢复同一 block ID、连接关系、可执行轨迹、最后事件、场景状态和计数，但不能自动再次弹出成功或重复记一次完成。

写入失败时，真实编辑留在内存与 Blockly 画布中，显示“重试保存”；成功重试保存同一草稿。多标签冲突继续提供备份/重载/重基操作；无 Web Locks 时两页均 fail-closed。

若当前 V3 中 w1-m2 session 损坏，加载流程必须保留原始损坏字节供家长下载，并从合法 snapshot 恢复；若无合法 snapshot，则回到安全初始进度。恢复后的 block ID 和轨迹必须仍可真实执行。

## 跨关与家长影响

- 完成 w1-m2 持久化后解锁 `w1-m3 四海披挂`；刷新后仍解锁。
- 关卡星级按实际使用的不同提示层级计算，沿用 0/1/2+ 层提示对应 3/2/1 星。
- w1-m2 的 attempts、hints、运行次数和调整次数进入第一周家长周报。
- 连续出现运行失败时，第一周“需要留意”必须能显示与本关目标一致的“数值比较”，不能只报告第一关的顺序问题。
- 第二关不发放装饰性货币、装备或神兽成长；尚未实现真实跨系统效果时不新增这些系统。

## 无障碍与失败处理

- 支持鼠标、触屏和键盘按钮完成添加、移动、删除、清空、运行、回到问题积木和重播。
- 错误反馈使用聚焦的 `role=alert`；播放结果使用礼貌 live region。
- 320px 页面无整页横向滚动；Blockly 只能在自己的受控区域内滚动。
- 减少动画时同一事件序列立即落地到同一最终状态；静音在执行前开启时不得发起成功音频播放或请求。
- 场景、Blockly、存储 lazy chunk 加载失败时，保留页面其余内容和显式重新加载动作。
- Phaser 图片加载失败时显示本地重试；重试、卸载和快速重播不得由旧场景回调污染新状态。

## 预先固定的性能预算

以下目标在实现前固定，不因实现超限而事后放宽：

- 首页入口静态 JS：不超过 180 KiB gzip；
- 首页保守总量：不超过 650 KiB；
- Phaser 动态依赖：单块不超过 1600 KiB raw；
- 每个正式 Phaser 场景运行闭包：不超过 1900 KiB raw；
- `w1-m1` 冷加载响应体：继续不超过 `2.5 * 1024 * 1024` B；
- `w1-m2` 冷加载响应体：不超过 `2.5 * 1024 * 1024` B；
- 两关共用正式龙宫媒体总量：不超过 `1.25 * 1024 * 1024` B；
- 单张 raster：不超过 512 KiB。

w1-m2 的体验、Blockly 工具和 Phaser 场景必须由路由动态加载。冷加载门禁拦截 service worker、禁用缓存、收集所有 HTTP(S) 响应体，并对重定向、304、请求失败、非 2xx 和无法读取的成功响应 fail-closed。

## RED→GREEN 验收与真实浏览器证据

所有生产行为先有失败测试并确认因缺少行为而失败，再写最小实现。

### 自动化验收

- w1-m2 积木注册、任务白名单、连接编译、重排/删除/断链与跨关积木混入。
- 正确轨迹、错误选择、错误顺序、重复动作、不完整程序、零惩罚和确定性重放。
- w1-m2 draft 保存/恢复稳定 ID；Progress V3 严格解析、canonical run、防篡改、导出导入和损坏 snapshot 恢复。
- 会话写入失败保留真实草稿并可重试；CAS、多标签、clear 和无锁行为继续回归。
- 完成只在播放结束发生一次；刷新不重复完成；w1-m3 解锁和家长周报反映 w1-m2。
- 类型检查、资产清单、动态加载与固定包体预算全部通过。

### 五项目真实浏览器矩阵

支持目标保持为：

1. desktop Chromium 1440×1024；
2. tablet WebKit 768×1024；
3. touch Chromium 390×844；
4. desktop Firefox 1440×1024；
5. narrow touch Chromium 320×844。

五个项目都必须从仅含已完成 w1-m1 的合法测试前置开始，不注入 w1-m2 完成或 session。每个项目都通过可见控制：

1. 进入 w1-m2；
2. 建立“查看重量 → 选择 7200 斤方天画戟 → 缩小”错误链；
3. 运行并看到方天画戟错误动作、阻挡效果和聚焦问题积木；
4. 真实移动/删除/添加 Blockly 积木，改成选择 13500 斤定海神针；
5. 运行事件播放到完成；
6. 刷新并证明同一 block ID、轨迹、事件、状态和计数恢复；
7. 返回地图证明 w1-m3 解锁；
8. 验证当前 viewport 无关键内容裁切，320px 无整页横向滚动。

附加浏览器路径覆盖：写入失败与可见重试、损坏 V3 snapshot 恢复、键盘完整操作、减少动画/静音等价、场景与工具 lazy 失败、w1-m1 与 w1-m2 各自冷加载预算、家长周报与 V3 导出导入。

测试允许在首次加载前设置“仅 w1-m1 已完成”的合法夹具来解锁目标关，但不得注入 w1-m2 的积木、轨迹、session、事件或完成状态。成功断言必须全部来自可见 w1-m2 Blockly 和应用控制。

## 交付报告

最终证据文档必须给出：

- 实现 SHA 与证据 SHA 的区分；
- RED 失败和对应修复；
- 单元、类型、资产、包体和五项目浏览器的精确数量；
- 两关冷加载的实际字节与余量；
- w1-m2 截图原尺寸检查结论；
- 达成等级、未验证范围与剩余风险。

只在全部本关证据满足时报告 `w1-m2：One-level playable`。任何强制项缺失都报告 `not complete`，且永不外推为 30 关、完整系统或商业生产完成。
